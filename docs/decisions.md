# Design decisions

| # | Decision | Why | Alternative rejected or deferred |
|---|----------|-----|---------------------------------|
| D1 | Thursday build is a small pilot (10 workers × 10 dates, 44 same-partition shifts); the full 30 × 60 design is one flag away | A small version that runs end to end shows progress and lets us find problems cheaply | Full design only: slower to debug |
| D2 | Report danger-event counts as they are; never lower the danger limit or raise workloads to create events | Tuning the experiment until it "works" is a form of bias | Changing limits after seeing results |
| D3 | PHS is run one minute at a time, carrying body state between minutes | Weather changes during the shift; pythermalcomfort 4.8.0 accepts and returns the state needed | One steady PHS run per shift: ignores changing weather |
| D4 | Logistic regression first; random forest and gradient boosting in Week 8 | Fast, explainable, enough to prove the pipeline | Deep learning: too little data, harder to explain |
| D5 | One-screen Streamlit dashboard | It is the demo for the lab and the symposium | Separate evaluation app: not needed |
| D6 | Messages replayed in Python on MQTT-style topics, no broker | Tests the message format and fault handling with less infrastructure | Mosquitto broker: network behaviour is out of scope |
| D7 | Workers are balanced across acclimatisation × work-rate groups, and every partition gets every group (stratified split) | Unbalanced splits left test sets that could not contain danger events (see iteration log) | Random split; balancing acclimatisation only |
| D8 | Direct sunlight faded in between cos(solar zenith) 0.05 and 0.15 in the WBGT calculation | Hour-averaged radiation divided by a tiny cos(zenith) gave impossible sunrise WBGT values; a hard cut-off caused a 2 °C jump | Using the raw value; a hard cut-off |
| D9 | Air speed for PHS = 10 m wind × 0.75, clipped to 0.2–3.0 m/s | PHS needs air speed at body height and has a valid range of 0–3 m/s | Using 10 m wind directly |
| D10 | (Proposed, under review) Latency is measured two ways: processing time per wearable message (message in, alert decision out), and fault-detection delay (minutes from the first faulty heart-rate reading to WBGT fallback, and back to ML after the fault) | Tutor feedback (29 Oct) asked for explicit latency measures. With one-minute messages, a decision must finish well inside 60 s; fallback must start within the configured limits (2 min offline, 5 identical readings) | End-to-end network latency: there is no broker or device (D6), so it would be invented |
| D11 | (Proposed, under review) Usability is measured by alarm burden (warning minutes and false alarm episodes per shift, already in E3) plus a heuristic evaluation of the dashboard against Nielsen's 10 usability heuristics by two group members | Alarm burden is the usability problem that matters most for warning systems (alarm fatigue). A heuristic review needs no outside participants, so the "no human participants" statement in Section III stays true | User study with classmates (e.g. SUS questionnaire): involves human participants and would need ethics clearance |
| D12 | Heart-rate readings outside 30–220 bpm are treated as missing (finding F2), so a faulty sensor triggers the WBGT fallback. Decided by Rayen, 8 Nov 2026 | Values below 30 or above 220 bpm are not plausible for healthy adult workers; the simulated heart rate stays well inside the range, so results are unchanged | 40–200 bpm: could discard real readings from fit or young workers. No check: garbage values would reach the model |
